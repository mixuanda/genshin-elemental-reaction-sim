# 确定性周期实体与动作条件检查点

本增量让主模拟器对有限、确定性、无附着引擎的周期实体及动作起手条件导出完整相位状态。它没有另建计时器，也没有把随机起步诊断改称稳态。

## 实际导出

`PeriodicEntityRuntime.captureState()` 提供真实活实体及最近代次计数。检查点读取同一次主队列快照，收集活实体、已被替换但取消任务尚未执行的旧实体，以及已产生延迟命中的历史实体。后者即使被替换，已经排出的伤害仍然执行。

同一持有者、同一实体定义下，以真实最近代次为基准保存 `relativeGeneration`。绝对递增编号只用于日志命名，运行时存活判定使用对象身份；导出保留每个引用之间的身份关系、当前存活标记、代次差、出生年龄、剩余期限与接受动作。不同代次关系不会被统一删成“有一个实体”。没有活实体或在途引用的旧计数只影响将来日志编号，不加入状态相等判断。

检查点保存下一次真实 `periodicEntityTick` 的帧、tick 序号与存活／取消决定；已排命中保存原始 `snapshots`、`periodicFlatSnapshots` 及来源实体、tick 序号和取样年龄。旧 tick、伤害以及未来动作的同优先级 FIFO 顺序按实际队列保留。纯审计绝对队列序号被移除，排序结果保留。

动作生命分支从实际 `actionConditionLog` 读取，包含取样时生命／最大生命、完整条件定义、选中结果与起手优先级，不使用现在的生命重新计算过去。仍有后续任务、实体或动作占用的接受动作保留锁定上下文；已无后续影响的纯历史日志不进入周期状态。动作 priority 8 及其同帧自产效果的 +10 顺序继续使用主队列原规则。

新增能力标记只有收到真实运行态及接受动作记录时才解除对应阻塞。未配置这些功能时，原检查点的 JSON 形状不增加周期实体或条件字段。附着、目标时钟、随机暴击、普攻随机回能、西风、概率产球及未导出的触发状态仍保留各自阻塞。带 Aura 的久岐忍来源配置因此仍不能证明完整确定性稳态。

## 有限尾段

新增共用 `action-pending-horizon.ts`，同时供动作检查点和稳态起步计算使用。周期实体执行“先 tick，再检查到期”，因此最后一个可能执行的 tick 相对生成时刻为：

`firstTickDelay + max(0, ceil((duration − firstTickDelay) / interval)) × interval`。

尾段再包含生成延迟、该 tick 的伤害延迟和命中产球的旅行时间，覆盖全部候选条件命中，以及原有扣能、体力、治疗、召唤及其他延迟任务。不能用仅有声明 duration 的截断窗口证明重复状态；缺失活实体的下一次主队列任务也会阻塞。

`npx vitest run packages/sim-core/src/__tests__/periodic-phase-checkpoint.test.ts`

实际观察结果：

1. 同一次连续运行以 120 帧为输入周期，预热 9 周期，再保留 650 帧完整尾段，总长 1730 帧，测量窗口为 `[1080, 1200)`。实际完整状态重复并建立 period 1，窗口有 2 个伤害事件。各比较边界都保留代次 `−1` 的取消 tick 与代次 `0` 的活 tick；任务剩余帧分别为 0、120，历史取样伤害分别在 50、170 帧后执行。旧伤害依然引用旧实体及其 EM 200 取样。动作输入优先级为 8。
2. 同样满生命时，早期边界只有代次 `0`，后续边界有 `−1 / 0`，状态不同。一次临时精通增益已结束后，在途伤害仍保留 EM 400 的旧取样；后续代次保存 EM 200，不能被当前面板覆盖。两个分支场景治疗后生命相同，但起手 40%／60% 生命锁定的真／假分支仍不同。
3. 声明 duration 901 帧、首次 tick 1000 帧、命中延迟 230 帧时，真实尾段为 1230 帧。12 周期预热加尾段总长 2670 帧；缩为 600 帧的观察输入被明确判为截断。仅有配置而没有真实导出时仍阻塞；即使周期和条件状态齐全，Aura 或随机回能仍独立阻塞。

两个已有专门场景原先断言“周期／条件不支持”，现更新为它们实际短窗口的“检查点之后不足两次完整输入周期”；本轮没有重跑旧测试。没有运行全量测试、统一构建、性能测量或 Monte Carlo。统一构建及产品界面验证由主任务分别记录。
