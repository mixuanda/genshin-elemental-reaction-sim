# 祭礼真实串行充能：浏览器专项记录

本专项新增 `apps/web/e2e/sacrificial-runtime.spec.ts`，仅一条综合正常 UI 流程。根任务统一生产构建通过后，复用既有 `127.0.0.1:4173` 预览运行。**首跑 1 failed / exit 1；修正测试场景的行动等待模式后，仅复验此同一条，1 passed（2.4 s）/ exit 0。** 没有把首跑计为通过，也没有修改生产逻辑或放宽数值期望。

没有执行旧流程、额外核心测试、性能测试、蒙特卡洛矩阵、另行构建或重启服务。分析步骤仅选择一个预热周期；其余为本次功能必需的主模拟、预览与 JSON 重载。

## 两次实际运行

首跑命令：

```sh
GIDPS_PREBUILT=1 npx playwright test apps/web/e2e/sacrificial-runtime.spec.ts --reporter=line --output=test-results/sacrificial-runtime
```

主队伍和行动编辑、第三次战技实际开始帧、冷却队列、粒子与能量、可见账本、命中回填和完整记录 JSON 的断言均已通过；最后的预热检查失败。测试起初沿用严格模式，而 11 秒周期后的第二轮不能立即重复耗尽两次串行充能。产品正确报告：`commands.5 [ABILITY_ON_COOLDOWN]`，最早第 1207 帧可施放，因此尚未进入要检查的随机状态检查点判定。这是测试场景与目标不匹配，不能将该结果假装为稳态检查已完成。

定点修正只有在正常行动页显式选择 `#rotation-mode = wait`，允许后续周期按真实剩余冷却等待。首周期的第 1、2、10 帧、伤害和队列等全部原断言保留。复验命令：

## 正常 UI 路径

导入明确标注为合成验证的两充能战技配置，最初没有祭礼模型，只含两个合法 E 请求。角色 90 级、ATK 1000、CR 0、ER 100%，敌人 90 级、物理抗性 10%；战技系数 1、伤害延迟 6 帧、取消与动作末帧均为 1、冷却恢复 600 帧、两次充能。每次实际战技在第 6 帧生成一枚同元素火粒子，飞行 2 帧，初能为零。

通过普通队伍页启用祭礼、为角色 `a` 选择祭礼剑 R5，保存配置。普通行动页选择自动等待，冷却开始时点明确填 0，并用“添加行动”加入第三次 E、请求帧填 10。实际 Worker 预览先显示第三次 E 在 10 帧执行；再正常保存并运行。没有注入运行结果或绕过普通控件。

固定本地种子为 `sacrificial-consumer-reference`。R5 成功概率 0.8，首次实际抽样为 `0.6284964594524354`，满足严格小于概率而触发。后续两个命中受祭礼冷却阻塞，不重复消耗抽样。

## 同核心重现与稳态限制

选择第三次战技在第 16 帧的真实伤害，通过已有按钮打开独立计算器。原逐段公式与计算器的全部可见轨迹一致，重现差值为 **0**。导出捕获命中再导入，差值仍为 **0**，捕获源结果保留祭礼判定和串行冷却日志。完整模拟记录导出后更改种子，再导入原记录，原种子、配置、选项、祭礼日志、冷却队列、粒子与能量记录均恢复一致。

随后一次连续预热得到 `steady-state-not-established`，`checkpointCoverage.complete = false`。页面与导出记录均明确说明：**祭礼独立随机流、实际技能串行充能及延迟冷却任务尚未纳入完整周期检查点，不能据此证明确定性稳态。** 没有仅凭相近伤害或能量结果显示已建立稳态。

该流程是一个显式合成场景对固定来源实现的正常产品路径验证，不是实际角色构筑、游戏实测或与 gcsim 随机序列匹配证明。运行时仍采用无角色卡肉的来源范围；未扩展覆盖所有精炼、武器、命中回调和延迟冷却组合。
