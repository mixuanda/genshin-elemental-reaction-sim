# Source-host RNG policy receipt — source audit

- Both pinned Go toolchains, `go1.25.0` (Classic) and `go1.27.1` (Stellar), have the same `math/rand/rng.go` `rngSource.Seed` steps: signed seed modulo `2147483647`, add that modulus to a negative remainder, then replace zero with `89482311` before initializing the generator vector.
- Both source-host entrypoints parse the request seed with `strconv.ParseUint(..., 10, 64)` and pass `int64(seed)` to `simulation.NewCore`. Both native `core.New` implementations use `rand.New(rand.NewSource(opt.Seed))`. The receipt records the original request string, the signed conversion, and the seed actually supplied to `rngSource` initialization after its normalization.
- Thus distinct uint64 inputs can start the **Core.Rand** generator in the same state: `1` and `2147483648` both normalize to `1`; `0` and `89482311` both normalize to `89482311`. A distinct input string is not evidence of a distinct initialized Core.Rand stream, and distinct effective seeds alone do not prove statistically independent outcomes.
- `critPolicy`, `criticalTriggeredEffects`, and `otherRng` in the receipt describe native sampling policy; the receipt does not draw random values or change gameplay. A production import audit of both pinned source trees found no simulation-time call to the package-global `math/rand` generator. In `pkg/core/info/shape.go`, `rand.Float64()` is called on the injected `*rand.Rand` parameter, and every production `CalcRandomPointFromCenter` callsite passes `c.Rand` or `c.Core.Rand`. `pkg/simulation/randstats.go` receives `core.Rand`; combat selection receives that same pointer through `core.New`; configured random energy/hurt events use `s.C.Rand`. The remaining `math/rand` uses are local RNG construction in the optimization runner and backend sharing helpers outside source-host simulation. No RNG-routing patch is needed for these pinned trees.
