# 可编辑例题

例题入口为 `/examples`，点击“加载这个例题”后进入 `/calculator`。例题保存的是实际 `CalculatorDocument` 输入，调用与用户计算相同的 `calculateDocument()`；界面从此次执行的 trace 渲染公式、代入和中间值。修改面板、倍率或目标后必须重新执行，不能只更新最终数字而保留旧解释。

例题明确分为 `synthetic` 合成教学、`source-backed-game` 真实角色来源交叉核对、`verified-game` 已完整核验真实游戏，以及 `blocked` 缺少证据的分支。合成数据不进入正式角色选择器。凯亚最小真实配装已进入来源交叉核对类别，但仍保持 `provisional`，不会仅凭固定来源一致就升级为当前版本游戏实测已验证。

下述 A/B 数值是验收基准与手算说明，不是额外的运行时代码。实际执行测试及命令结果见 [qa-report.md](qa-report.md)。

## 例题 A：从基础攻击到期望伤害

这是普通伤害的合成算术输入，不代表某个真实角色或装备。角色和敌人均为 90 级，相关抗性为 10%，没有减防、防御无视、反应或特殊独立乘数，伤害允许暴击。

| 输入 | 表单值 | 含义 |
| --- | ---: | --- |
| 角色基础 ATK | 300 | 与武器基础 ATK 相加 |
| 武器基础 ATK | 700 | 构成基础攻击力 |
| 攻击力百分比 | 0.80 | 80% ÷ 100 = 0.80 |
| 固定 ATK | 200 | 在百分比加成之后加入面板 |
| 天赋倍率 | 2.00 | 200% ÷ 100 = 2.00 |
| 独立基础伤害加算 | 300 | 在天赋倍率作用之后加入伤害 |
| 适用伤害加成 | 0.50 | 50% ÷ 100 = 0.50 |
| 暴击率 | 0.70 | 70% ÷ 100 = 0.70 |
| 暴击伤害 | 1.20 | 120% ÷ 100 = 1.20 |

| 阶段 | 实际代入 | 结果 | 解释 |
| --- | --- | ---: | --- |
| 基础攻击力 | 300 + 700 | 1,000 | 角色与武器基础相加 |
| 最终攻击力 | 1,000 × (1 + 0.80) + 200 | 2,000 | 百分比只乘基础，固定 ATK 再加入 |
| 天赋缩放 | 2,000 × 2.00 | 4,000 | 倍率读取最终 ATK |
| 基础伤害加算 | 4,000 + 300 | 4,300 | 这里的 300 是伤害，不是固定 ATK |
| 伤害加成 | 4,300 × (1 + 0.50) | 6,450 | 对当前基础伤害应用适用加成 |
| 防御倍率 | (90 + 100) ÷ [(90 + 100) + (90 + 100)] | 0.50 | 同等级、无减防与无视 |
| 防御后 | 6,450 × 0.50 | 3,225 | 将防御倍率作用于伤害 |
| 抗性倍率 | 1 − 0.10 | 0.90 | 本例落在普通非负抗性分支 |
| 抗性后 | 3,225 × 0.90 | 2,902.50 | 得到未暴击伤害 |
| 反应 | 无增幅 | 2,902.50 | 无反应不会凭空产生增幅 |
| 非暴击 | 2,902.50 × 1 | 2,902.50 | 保留基准伤害 |
| 暴击倍率 | 1 + 1.20 | 2.20 | 暴击额外增加 120% |
| 暴击伤害 | 2,902.50 × 2.20 | 6,385.50 | 允许暴击时的暴击结果 |
| 期望倍率 | 1 + 0.70 × 1.20 | 1.84 | 用暴击概率加权额外伤害 |
| 期望伤害 | 2,902.50 × 1.84 | 5,340.60 | 同条件下的概率平均 |
| 加权复核 | 0.30 × 2,902.50 + 0.70 × 6,385.50 | 5,340.60 | 与概率加权的两种结果一致 |

独立加算的 300 不乘天赋系数；若误填到固定 ATK，它会先进入面板，再乘 2.00，得到不同结果。期望值不是保证出现的单次游戏跳字。没有给出持续时间，所以这仍是伤害，不是 DPS。

可编辑练习：只将固定 ATK 从 200 改为 300，检查最终 ATK、天赋缩放及后续伤害随之更新；再只更改独立基础伤害加算，比较它进入公式的位置。两者应在 trace 中显示不同的依赖步骤。

## 例题 B：两段伤害的独立反应覆盖

本例明确从“所有其他非暴击因素已经结算，但尚未反应和暴击”的入口开始。它没有伪造前置 ATK、天赋或敌人拆分。A 段入口伤害为 1,000，B 段为 600，暴击率为 0.70、暴击伤害为 1.20；条件假定只有 A 段获得 1.50 倍增幅，B 段倍率为 1.00。没有暴击触发效果或暴击结果改变后续状态的反馈。

页面只显示本例使用的共享暴击率/暴击伤害和各段入口伤害/增幅倍率，隐藏无关的普通基础面板及目标编辑器。无需填写或臆造一套装备来重现本例。

| 阶段 | 实际代入 | 结果 |
| --- | --- | ---: |
| 期望暴击倍率 | 1 + 0.70 × 1.20 | 1.84 |
| A 段期望伤害 | 1,000 × 1.50 × 1.84 | 2,760.00 |
| B 段期望伤害 | 600 × 1.00 × 1.84 | 1,104.00 |
| 一次施放总伤害 | 2,760.00 + 1,104.00 | 3,864.00 |

反例独立显示在正式合计之外：

| 错误操作 | 实际代入 | 结果 |
| --- | --- | ---: |
| 将第一段增幅错误复制到全部段数 | (1,000 + 600) × 1.50 × 1.84 | 4,416.00 |
| 高估量 | 4,416.00 − 3,864.00 | 552.00 |

反例同样由核心表达式计算，不加入正式总伤害。修改 A/B 输入或反应倍率后，正确合计与错误捷径一起重算；不把固定 552 写进页面。

本例的反应资格由教学输入指定。它不证明任何真实角色第一段必反应、第二段必不反应。真实轮转需要动作、附着、元素量、ICD 与敌人状态证据。无时间分母时只报告技能伤害。

## 资源、层数与队友贡献表达式

`resource-expression` 使用 `baseDamageFormula`，明确教学规则为：资源小于 1 时基础伤害为 0，否则基础伤害为 `ATK + 0.1 × HP + min(stacks, 3) × teammateAtk × 0.1`。这是假设性教学表达式，不对应真实角色。后续适用的伤害加成、防御、抗性和暴击继续使用共同核心。

ATK/HP 来自解析后的当前面板；`resource`、`stacks`、`teammateAtk` 在表单中独立编辑，保留单位、来源、含义及队友 `ownerId`。表达式、输入和规则 ID 随计算 JSON 导出。编辑资源跨过门槛或层数超过上限时，应从同一 trace 看到条件/上限实际参与计算，而不是页面另行编写一个相似解释。外部资源输入不能覆盖 `atk`、`hp`、`def`、`em` 这几个核心面板变量。

真实技能中的 `additiveBaseFormula`、`damageBonusFormula` 和 `resistanceReductionFormula` 也使用这套资源输入界面，但分别作用于基础伤害附加量、来源伤害加成和来源减抗。界面显示实际规则、单位、范围及突破要求，来源表常量保持只读；不能把一个可编辑资源框误解为对应整套角色机制已验证。

洛恩来源动作的争胜实际消耗量使用已审阅 `allowedValues=[20,40,60,80,100]` 下拉档位，JSON 导入也接受相同约束。它表达已核对的生产界面条件，**不证明游戏资源只能以 20 递增**。资源增量只放大 `ATK×天赋倍率`，不放大额外固定附加基伤；乘兴实际技能等级与 A4 状态仍由输入恢复。镂骨彻心是部分动作，爆发六斩为完整条件动作，仍不是自动资源/轮转模拟。

莉奈娅 A1 示例须明确突破、露米在场、目标附近及月兆人数。共享减抗 AST 执行突破≥1时的条件：人数<2减岩抗 0.15，≥2为总量 0.30。最终抗性覆盖留空时执行这份来源减抗；填入已结算 `effectiveResistance` 后，来源表达式保留为 `not-applicable` 审计，不再扣一次。最终面板转换和 JSON 回放应保持同值。露米双击只是一组部分动作，不能据 25 秒持续时间猜轮数或把月结晶 Hammer/Crush 合入。具体数值、来源和已执行核心记录见 [来源上下文](cross-validation/lohen-linnea-context.md)。

## 奈芙尔普通命中：命座、消耗与本段精通

正式角色计算器的命座选择器支持 C0–C6 已映射普通 E/Q 条件。初始 E 不再套用只适用于幻戏的帷幕倍率；来源对施放状态先后仍不完整，E 保持部分动作。普通 Q 两段可编辑实际消耗帷幕，C0/C1 为 0–3，C2–C6 为 0–5；有效天赋等级由输入确定，切换 C3/C5 不会再自动加 3。

逐段将“满层精通增益仍有效”与“Q 本次消耗层数”分别输入：突破≥1、月兆≥2时，前者在 C0/C1 提供 100 EM，C2–C6 提供 200 EM，后者替代 100。Q 消耗后增益仍可能有效，不能用消耗层数推断精通状态。选择“输入面板尚未包含”才执行本段另加；已在最终面板时，来源公式仍展示但乘零记账，不再重复加入。每段可有独立状态，JSON 和最终面板转换保留这种差异；重新导入最终面板默认回到“已包含”。

来源专项采用有效 Q 等级10、ATK2000、原面板 EM100、月兆2、双方等级90、基础草抗10%、非暴击：C2 消耗5层且另加有效200 EM为 `35481.888`；只关闭独立精通增益为 `30023.136`；消耗0层但保留增益为 `11827.296`；C4另明确目标正受20%减草抗为 `41395.536`。这些实际测试数字来自 [奈芙尔上下文记录](cross-validation/nefer-ordinary-context.md)，可在同一计算核心编辑复现，不是完整轮转或游戏实测。C4 条件包含实际4.5秒残留，但计算器不自动推断进入影舞、离远或到期；幻戏、C1/C6月绽放实体也未加入普通 E/Q。

## 特殊分支的编辑与解释

特殊教学条目调用 `special-calculator.ts`，沿用同一份计算文档、表达式执行和 trace 渲染，不在页面另算数值。界面为每位已有参与者提供独立表单：直接能力输入最终缩放属性及天赋系数，排名反应输入参与者等级及明确的等级反应基数；另可编辑元素精通、暴击率/伤害、专属基础提升、专属反应加成、特殊加算与擢升倍率。抗性在特殊分支单独输入，星导直接能力还有 `0–12` 极星领域计数。

这些字段才是特殊公式入口。普通 ATK 面板、敌人防御和普通伤害加成不会参与该特殊分支，界面隐藏无关普通面板/目标控制并明确说明。等级基数不是自动查表结果；修改等级时用户需同时提供有依据的对应基数，系统不插值、不猜测。`assumed-enabled` 明确假定已启用；改为 `disabled` 或 `unknown` 时，特殊公式阻塞，不继续显示一笔已启用的特殊伤害。

若参与者含有 `specialBaseBonusRules`，界面显示月兆规则及其 `providerId`，并将提供者 `maxHp` 作为独立来源快照输入。创建条件化副本后可以单独编辑此生命值，与直接伤害缩放生命值分别重算；改变一个不会自动改另一个。共享核心执行来源规则及上限，实际 `state-resolved` 事件的这些字段只读。

直接能力的缩放起点与反应的等级起点分别展示。在当前来源规定的多人排名分支中，每种独立暴击组合分别计算贡献、排序和加权，再按组合概率求和；不能先平均贡献再排序，也不统一套一个最终暴击倍率。至多四位参与者会枚举至多 16 种组合，详细公式和中文解释与实际执行一起生成。此计算显式假设独立暴击且没有暴击触发反馈，不证明实战参与资格、领域计数或事件时序。两个非伤害特殊事件只说明状态/生成事件，不产生直接伤害。

选择“月绽放 · 草露与已声明能力”后，可以只运行普通绽放与草露生成；转换本身不造成一笔额外伤害，普通草原核仍保留。参考范围为水／草／物理、aura-v5、legal-frame-v1、60 FPS、单个静止范围内目标，无目标移动/阶段、卡肉、玩家受伤反馈、手工反应覆盖或执行插件。月绽放依赖 aura-v5 的真实普通绽放与草原核，不能沿用其他独立分支或 LC＋LCrys 共享入口的 aura-v3；切换分支会清除旧 Aura 覆盖勾选，需要时明确选择只修改本次运行副本。身份映射与当前输入决定资格，不补造角色技能。

需要加入来源月露涤荡时，使用正常入口“本次运行加入月露涤荡”，而非先手写一个空命中动作：

1. 在主工作区使用合法帧行动时间轴，配置实际水/草附着与普通绽放；在分支中明确映射哥伦比娅角色。
2. 在 `data-lb-source-action` 选择该角色，填写运行副本最终请求开始帧、有效普攻天赋、突破与 C0，勾选“本次运行明确加入一次来源月露涤荡”。这些值不会默认补齐。
3. 运行副本通过 `createMoondewCleanseAbility()` 添加来源重击及末尾 `charge` 指令。新增帧不再次叠加主工作区已应用的执行延迟，既有命令与全局编辑配置保留；具体追加内容进入 `explicitConfigurationChanges`。不会自动切人或补资源，实际采用帧及阻塞原因以执行审计为准。
4. 展开已结算月露涤荡事件，查看段序号、实际草露消费凭据、独立取样面板和 trace，再点击“在独立计算器中还原本次命中”。

当前来源能力限 C0、闲置起手；动作开始前必须已有草露，同帧稍后生成的一层不能倒用于起手。来源规则在起手后第 55 帧消耗一层，在第 62、70、92 帧分别读取 HP、EM、CR、CD 与草抗并结算。124 帧是本参考配置采用完整动画、禁止提前取消的锁，不是游戏最早可取消帧。没有取消/连携支持，前序动作未结束或锁内启动其他动作会阻塞。三段没有普通附着，也不能另外再加一套普通攻击伤害。

高级折叠区保留已有空命中动作绑定入口，适合已编排时间轴；核心仍要求同角色来源 `charge`、124 帧锁、零冷却且无其他命中、效果或取消覆盖，不能仅凭名字或空命中就认定是月露涤荡。当前只接入这一直接能力及固有月兆来源提升；领域、月岭露、Gravity、其他命座及其他角色的直接月绽放不在此范围。

`simulateLunarBloomProfile()` 的特殊事件保存来源能力执行信息、实际资源凭据与每段快照，`lunarBloomEventToCalculatorDocument()` 通过共享特殊公式重算后生成只读 `state-resolved` 文档。创建条件化副本后才允许改动参与者数值与月兆提供者生命值，新结果不再声称复现原事件。这里描述实际代码入口与使用步骤，不新增 `verified-game` 例题，也不宣称这些步骤已通过 UI 测试；命令、实测结果及限制仍以 QA 报告为准。

## 真实目录基础配装与教学输入

正式角色入口可使用来源装备推导编辑器，按精确等级曲线、突破记录与合法武器档位解析基础属性；圣遗物支持实际部位、套装、稀有度、等级、主词条、初始副词条数量和逐次强化档位。主副词条从固定来源精确查值，重复部位、非法主词条、主副同名和不合法强化历史不能当作有效配装。编辑器在正式角色选择后按需加载，不把合成基础值包装成真实装备。

已映射的武器/套装条款可分别明确启用，生命比例和目标附着等状态必须显式输入；元素、攻击标签和武器种类由共享核心逐段检查，不能把普攻专用增伤施加给战技。未实现角色/武器被动、命座、套装条款和外部增益仍须明确停用，缺口保留在报告中。应用配装替换当前面板，绝不把装备属性再次加到导入最终面板。

元素集合选择先明确“未知／未提供”或“已确认当前状态”：未知会保持缺失，不能被当成 0；确认后不选任何元素才保存 `[]`，表示当前明确没有有效元素加成。烬城基础 12%/15 秒与额外 28%/20 秒分别填写元素集合，可表达基础窗口已结束而额外窗口仍有效。黑曜二/四件状态和匣里日月两个 6 秒窗口同样独立，不把其中一项状态复制给另一项。磐岩/天赐秘仪的元素类型和数量限制由核心检查，不能重复选择同一元素叠加加成。

此前武器/四件套增量执行共享 AST 与反应专用协议，状态、层数和窗口仍是用户显式输入；部分条款可算不等于整件装备全部触发、额外攻击、能量和持续机制完成。64 项装备核心定向记录见 [装备增量](equipment-additional-implementation.md)，来源公式核心记录见 [洛恩/莉奈娅上下文](cross-validation/lohen-linnea-context.md)；此前来源/装备浏览器用例已实际通过，使用普通控件编辑资源、减抗和独立元素窗口；专项证据与整合检查见[QA](qa-report.md)。这些历史记录及文档编辑不代替新增奈芙尔、混合 v2 和启动分页的浏览器验收。

基础值、等级曲线、突破加值和逐项 `secondaryContributions` 来源进入共享 trace。采用 `core-sourced-v1` 的配装由核心计算适用来源增伤；界面输入的手动伤害加成只作额外补充。面板百分比/固定输入包含已有来源贡献，编辑后的差值作为手动调整单列，不再重复相加。基础属性与角色等级只能通过装备编辑器改动。该功能保持暂定证据，已支持的合法词条与有限条款不等于全部动态被动/套装机制完成，也不把真实来源例题自动升级为 `verified-game`。例题 A 仍为合成输入，B 与特殊分支仍使用其明确数值入口。

普通或剧变例题可逐段填写最终抗性覆盖：留空时核心应用目标抗性与适用的来源装备减抗，填值时表示减抗已经结算，不再重复扣除。来源配装中的反应加成框是额外手动补充量。切换最终面板会由核心逐段保存反应加成与最终抗性；同会话切回原配装恢复各动作的原补充输入，并解除展示柜面板与天赋绑定，避免后续动作再次注入展示柜最终增伤。应用新配装会清除旧的逐段增伤、反应补充量与抗性覆盖。比较不同输入路径时，应同时检查这一覆盖字段及 trace，不能只比面板 ATK。

## 复现方式

1. 从 `/examples` 加载例题，检查数据徽标为“合成教学数据”。
2. 在 `/calculator` 展开任一阶段，查看符号公式、变量、实际代入、中间结果与解释。
3. 编辑数值，检查受影响步骤即时重算；输入无效时不显示旧总伤害。
4. 切换单次命中/一次施放并选择包含的段数，检查合计与排除列表一致。
5. 导出计算 JSON，再导入；范围、面板模式、所选命中、假设、数据身份、资源输入、`gameContext` 与规则版本应保留。导出完整报告可查看此次执行的原始 trace。

这些步骤是产品使用与验收说明。已执行哪些自动化及浏览器检查、精度容差与实测输出，应以 QA 报告和对应日志为准，不从本文步骤推定测试已通过。
