# 帧精度、图表与新计算入口核查

来源引擎的模拟时间单位是 1/60 秒，不能等同实际游戏显示帧率或服务端精度，也不代表每帧均产生伤害。

## 已核代码与改动

- Classic b4ae769 与 Stellar a7dc4bf 固定源码 `pkg/simulation/run.go:286` 的 `nextFrame` 使用 `C.F++`，执行 Core.Tick、能量处理、受击处理和 OnTick；时长判断为 `int(Duration*60)`。没有重写引擎时间或额外重复计算空帧。
- TypeScript `packages/sim-core/src/simulator.ts` 的合法帧队列比较顺序为 `frame → priority → queueOrderSequence/sequence`。合法时间轴的帧和 `fps:60` 有模式/schema 约束；`toFrame` 对秒输入按 `Math.round(seconds*60)` 进入帧网格，不是先取整秒。实际 frame 输入保持整数；显示为 frame/60。
- 查到原网页无 timeline 的入口曾明确选择 `legacy-v0.1`。本轮 `app.ts` 与 `simulation-worker.ts` 的新计算/准备/批量入口统一为已有 `legal-frame-v1`。`new-simulation-options.ts` 复制运行参数，不修改保存的历史选项；新的显式重算采用帧模式，旧文件读取/导出和已有结果不因此重算。
- 显式历史核心 API 仍保留 legacy-v0.1，用于历史兼容；不能说仓库已完全没有秒时钟代码。独立单技能公式计算本身不是时间调度器，其明确上下文与原始命中帧保留。
- CD、粒子/固定能量到达、增益到期、同帧事件优先级、hitlag 仍沿用现有规则，不将它们简化为每秒检查。此前真实 VV 失效测试的 1081/1082/1083 帧证据保留，本轮没有重跑整个真实队伍矩阵。

## 曲线精度

默认改名“1秒汇总”。新增“逐击伤害（帧）”、整数起止帧范围、实际事件累计阶梯线和逐击原始明细；每笔保留事件 ID、帧、秒、角色、来源、元素/反应和伤害。同帧多击不去重；无事件空帧为零；DoT 只按捕获的实际 tick 呈现。

累计阶梯在命中帧垂直增加，事件间水平保持，没有平滑插值制造连续伤害。明细按需展开、每页最多50笔；曲线按实际事件构造，不为每个空帧生成庞大数组。筛选贡献表仍以完整窗口为分母，缩放只改变观察范围，有明确提示。显示数值会格式化，原始导出保留精度。

## 最新性能结论（不宣称本轮已稳定提速）

本轮加入仅用于诊断的阶段计时事件，不改变持久结果：

| 阶段 | 最后一次云端实测 |
|---|---:|
| Worker 首次消息（启动） | 0.304 秒 |
| 清单/WASM准备 | 0.494 秒 |
| 原生执行与共享公式 | 7.756 秒 |
| JSON解析 | 0.026 秒 |
| 结果语义校验 | 5.385 秒 |
| 传输与排队 | 0.087 秒 |
| 页面结果处理 | 0.419 秒 |
| 浏览器实际点击事件至两帧绘制 | **14.553 秒** |
| 自动化发起点击至结果可见 | **21.558 秒** |

此前 18.83 秒属于最后一行的自动化墙钟口径，不可与 14.553 秒直接比较并声称提速。新增测量揭示自动化操作等待约7秒，应将它与浏览器实际收到点击后的等待分开。分阶段值并非精确无缝分区，未单独计入的调度/绘制会留有差额。

本轮两项小优化：私有深度冻结解释的子对象也可安全复用；完整 native 数据校验后只校验新增结果元数据，不再次遍历全部 native schema。没有省略字段验证、数值核对或状态机制，旧保存结果在入口仍验证完整身份，非法产物元数据仍拒绝。但这轮采样没有证实总体提速，不能把公式 microbenchmark 或减少代码遍历当作实际延迟改善。后续应继续定位约5秒的语义校验热点，避免把已很小的图表/DOM耗时当主因。
